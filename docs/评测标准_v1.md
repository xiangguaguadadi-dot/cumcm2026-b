# 第三、四问本地评测标准 v1

冻结日期：2026-09-11。依据用户提供的《B题.pdf》第1至4页、附件1第1至3节、附件2第3至8节和第12节。当前未取得官方模拟器源码或可查阅的官方代码仓库；本文件对齐公开题面和通信协议，不能宣称与官方二进制逐次输出一致。

## 官方指标原样记录

| 字段 | 定义 | 来源与用途 |
|---|---|---|
| 测试案例编码 | 本地使用 LOCAL-v1 前缀，官方编码仅从官方取得 | 题目正式表1 |
| 清除干扰源个数 | 仅统计 clear 返回 success 的不同源 | 题目表1 |
| 平均定位清除时间（秒/源） | 本局总虚拟耗时 / 本局清除数 | 题目演练公式、表1 |
| 程序运行时间（现实秒） | enter 成功至测试结束；本地按单调时钟记录 | 题目附录3及表1 |
| 被清除干扰源个数的比例 | 本局清除数 / 本局真实源总数 | 演练公式；真值只供评测，策略不读取 |

清除0个时，均值无数学定义，本地记为 null，绝不把分母改成1。这是本地缺失值约定，官方界面的零清除显示未验证。正式环境的源总数不可直接获得，正式记录不推算未给出的清除比例。

题目没有公开一个将清除比例、虚拟耗时、现实耗时加权的分数。因此不造综合得分，不把毫秒级本地时间当成官方成绩。题设目标是确保全部清除后尽可能缩短虚拟任务时间。

本地比较先检查全部清除、正常退出、异常和时限。某个场景只要任一候选或基准案例不完整，该场景不给耗时提升排名；所有失败行仍保存。全通过后逐场景比较每局“秒/源”的算术均值，并记录最差局。这个跨案例汇总是我们固定的研发方法，不是官方未公开的总分公式。不同场景不合并成一个总提升率。

## 固定物理规则与计时

- 目标源在半径1800米圆域，10至16个、频道互异且为1至20。第三问全向；第四问必须同时有全向和定向。策略从(0,0)、频道1开始，不能读取源数、源位置、接收半径或类型。
- 接收半径1000至1500米；定向源覆盖朝向两侧各90度（含边界）。距离不超过5米且有信号返回 near；其他有信号位置返回带固定误差的 direction；无信号返回 no_signal。
- 测向误差有界±1度、同址固定；示向度保留2位小数。误差场概率分布和跨频道相关性属本地假设，见下文。
- measure 耗时 = 移动距离/5 + 是否换频道×1 + 5。
- clear 耗时 = 移动距离/5 + 3 + 成功×2。clear不改变测向机频道；20米内必成功、不受发射方向限制，已清除源不重复计数。
- enter和exit不增加虚拟时间。官方199秒示例纳入固定回归检查。
- 坐标有限且每个分量绝对值不超过2000000。频道允许整数值1.0，拒绝布尔、非整数及越界值；非法参数不移动、不增加计时。直接函数层以ValueError表示结构错误，并非实际HTTP响应。
- 虚拟限时360000秒；现实限时为enter后1200秒与25分钟窗口的较早者。支持注入时钟和延迟入场，已登记动作可完整执行，达到限时后新动作关闭。评测另有1205秒进程看门狗，覆盖策略不再调用环境的死循环；这是本地保护宽限，不把1205秒当官方限时。

## 冻结内容与已知不等价处

local_env.py、evaluate.py、evaluation中的固定案例和基准、规则测试及本文件的SHA256写入manifest_v1.json。每次跑评测前后校验。修改策略只动solver.py；如要修订评测规则，另建v2并在新规则下重跑所有对照，禁止悄悄更新v1的散列。

- 微秒计时：官方说明按微秒累计，却未说明半微秒的舍入方式。本地固定为每动作四舍五入到微秒后按整数累计。
- 几何边界保留1e-10米计算容差；官方数值容差未知。
- 本地直接函数调用不模拟登录、联网心跳、HTTP请求体校验、request_id服务端缓存、并发冲突或网络延迟。http_client.py保留实际官方接口入口。这些通信行为仍需Windows演练验证。
- 固定案例为自建数据；官方空间分布、随机数实现及误差场尚未知。即使本地全通过，也不称为官方验证。
- Python接口封装是代码约定，不是阻止恶意反射读取真值的安全沙箱。后续审查策略是否越界读取评测数据。

## 测试集和迭代程序

12组：面积均匀、正1度偏差、负1度偏差、共享平滑场、共享50米分块场、共享500米分块场、圆域边缘且最小半径、偏心聚簇、原点聚簇、最小半径、恰10个源、恰16个源。两道题各每组100局，序列化保存完整源列表和误差种子。

完整测试：2400个案例，当前候选与冻结基准首次各跑一次，共4800次任务。快速测试：每组前5局，共120个案例，首次两份策略共240次任务。后续默认复用经散列校验的冻结基准逐案例数据，实际只跑候选：快测120次、全测2400次。缓存的基准现实耗时是历史值，不用于与当前候选比较机器运行速度；如需重新计时或校验基准，添加--rerun-baseline。快速集是完整集子集，二者不可当成两份独立验证。种子5000至5099已在前次核查使用，因此这是固定回归集，不再声称是未见留出集。后续避免按案例ID专门优化；最终仍需新样本及官方演练。

本次将当前已交付的优化求解器固定为v1迭代基准；不是早先对照实验里的旧算法。初始candidate与该基准完全相同，配对耗时差应该为0。每次迭代保存候选代码提交、参数、评测散列、逐案例数据、各场景汇总及现实评测耗时，再决定是否接受改动。

建议先快速测试淘汰错误，再完整测试；候选稳定后用Windows官方演练校准，最后第三四问各3次正式测试及官方日志。虚拟的5秒检测不在现实中sleep等待；本地运行速度由策略计算和评测开销决定。
